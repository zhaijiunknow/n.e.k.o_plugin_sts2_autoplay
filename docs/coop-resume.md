# 本机猫娘联机：建房与续局

## 页面入口

新版 **STS2 功能 → 游玩控制 → 猫娘联机** 提供两个独立按钮：

- **新建联机房间**：`sts2_open_coop_room(host=true, resume=false)` → `start_coop_session`。
- **继续联机存档**：`sts2_open_coop_room(host=true, resume=true)` → `continue_coop_session`。

先暂停自动游玩，在主机主菜单操作。两个按钮的检查、执行和结果读取始终绑定主机，
不受当前活动实例影响；自动游玩仍绑定猫娘。猫娘未运行时会启动第二个窗口；上一局结束后
可复用主菜单或局末界面的猫娘窗口，无需每局手动关闭。页面最长等待两分钟，
其中猫娘接管探测最长 45 秒。接管失败明确警告，不自动开始游玩，不要重复点击建房。
状态显示当前插件对着「主机」还是「猫娘」；确认猫娘后再按需开启自动游玩。
联机地图参数仍在单独的「参数配置」页。

单人进度 `current_run.save` 与多人进度 `current_run_mp.save` 是独立槽位。已有单人局不妨碍
新建联机，也不需要放弃单人存档。两个按钮点击直接执行，无二次确认；新建也不因已有多人
存档而拦截，新局保存会替换原多人进度。要保留原局请点「继续联机存档」，续局失败只报错、不自动新建。

## 原因（按本机安装的游戏程序集核对）

1. 原建房代码强制 `StartENetHost(33771, 4)`；ENet 主机 ID 固定为 `1`。
2. 游戏原生 `NMultiplayerSubmenu.StartLoad` 在 Steam 已初始化时传入 Steam 本地 ID，
   而 `RunManager.CanonicalizeSave` 必须能在存档玩家列表中找到它。ENet 存档不含 Steam ID，因此会校验失败。
   之后即使绕过 ID 校验，原生载入仍会选择 Steam host，不能让本机直连客户端加入。
3. 原猫娘直连使用 OS 进程号作为玩家 ID，重启后改变；游戏 `LoadRunLobby` 拒绝不在存档里的 ID。
4. 原直连只处理 `InLobby`，遗漏游戏已有的 `InLoadedLobby`（读档大厅）协议。
5. 原防覆盖仅检查单人 Continue 按钮，漏掉独立的多人存档槽。

修复：新局使用固定猫娘 ID `2`；旧局从存档找出唯一非主机 ID，通过子进程环境变量
`STS2_COOP_NET_ID` 原样传递；复用进程时通过重连接口设置本次连接身份，不改存档里的 ID。按 ENet 主机身份进行内存校验，打开游戏自己的
`NMultiplayerLoadGameScreen`；客户端处理读档大厅并准备。游戏原生多人菜单的继续按钮也会为
可识别的本机双人存档走这条流程，Steam 存档保持原生流程。

自动恢复只支持本机双人、非每日/非自定义的普通联机存档。三人以上、无法确认归属、损坏或
不兼容的文件不会被自动转换。这里不实现进行中的房间断线重连（`Running`），只实现退出后的读档大厅续局。

## 已被隔离的旧文件

只读检查发现本机有 `current_run_mp.save.<时间戳>.VAL.corrupt` 文件，仍可读取玩家列表，
但未找到 `current_run_mp.save` / `current_run_mp.save.backup`。这表示游戏当前不会把这些文件当作
可继续的存档。**扩展名不证明一定坏了，也不证明一定能救回**：可能是身份校验，也可能是旧版本内容不兼容。

恢复前必须：

1. 退出主机和猫娘，备份完整的对应游戏档案目录（包括 `.backup`、`.corrupt`、history）。
2. 选定具体一局，核对时间、角色、章节、版本；不能仅选择文件名最新的一个，更不能改玩家 ID。
3. 在备份/独立测试档案上验证 JSON、游戏迁移和模型目录兼容性。已经进入 history 的结算局，
   游戏可能判为过期存档并清理，不能承诺可续。
4. 确认需要恢复且当前多人槽为空后，将选定的**副本**恢复为该档案下 `current_run_mp.save`，
   保留原 `.corrupt`。此写入必须由玩家明确确认，不能自动扫描后覆盖。
5. 使用修复后的 mod，在主机点「继续联机存档」或游戏多人菜单的继续按钮，等待猫娘加入并双方准备。
   若游戏报告版本/内容不兼容，停止，不要新建覆盖，也不要删除备份。

本次实现没有移动、改名、删除或覆写任何真实存档，没有自动挑选 `.corrupt` 文件恢复。

## 验证边界

纯测试覆盖 ID 恢复/不变性、Steam/多人歧义拒绝、插件动作分流/并发保护/接管失败提示、前端直接执行与请求期间禁用。
C# 编译使用当前安装游戏 API。真实 Godot 双进程打开大厅、退出后再次续局和旧文件兼容性仍需
安装修复版后的实机验证，离线测试不能替代这部分。

## 猫娘进程打开但没有入房（2026-11-28 排查）

这次不是入房等待时间不足：主机已加载本地 `0.1.11` 后，RitsuLib 的工坊更新检查触发
`3794941932` 下载，将订阅目录覆盖回 `0.1.7`。随后启动的猫娘加载旧 DLL，日志出现
`ReflectionTypeLoadException: get_RunModels ... SimulatedCombatState`，mod 初始化失败，
所以 `18081` 没有监听、自动入房驱动也没启动。主机内存里的新版仍能正常建房。

- `deploy-workshop.ps1` 现在同时写游戏的 `mods/nekospire`（校验三个核心文件 SHA-256）
  与工坊订阅目录。本机 v0.114.0 的 ModManager 在相同 ID 下优先本地同版/高版；
  因此工坊旧版下载不再替换实际加载的开发副本。真正更高版本仍按游戏原生规则优先。
  不取消订阅、不关闭其他 mod 的更新、不人为抬高版本号；已有可选散装立绘首次迁移，
  不覆盖本地已存在的立绘目录。部署前后检查游戏进程，运行中不覆盖 DLL。
- `GET /config` 补回 `coop_client_port`，避免插件返回 `catgirl_address_unknown`。
- `POST /config` 真正接受/校验 `coop_control_mode=hold|auto`。此前该字段被当未知字段
  忽略，插件以为接管成功，mod 驱动却未停手。`hold` 仅在当前进程生效、不写共享配置，
  且只在插件 15 秒请求租约有效时阻止自主对局操作；主菜单/大厅/选角仍能入房和准备。
  异步决策结束后再检查一次，丢弃接管前尚未完成的求解/LLM 决策。

检查顺序：先看猫娘进程是否成功加载 mod、客户端 `/health` 是否可达，再看主机
`/config` 是否给出正确端口，最后看大厅人数。不要通过反复新建房间排查，以免替换多人进度。
新增离线测试覆盖临时目录部署/工坊覆盖隔离/运行中拒绝部署，以及接管配置和驱动门禁；
不等同于已完成真实双进程入房验证。

## 现有猫娘进程复用

主机先验证猫娘端口的 `/config` 角色和重连能力，再调用 `prepare_coop_rejoin`：仅接受主菜单或
局末界面，暂停旧驱动并退出结算界面，不放弃正在进行的对局。主机大厅打开后调用
`rejoin_coop_session`，使用新局 ID 2 或旧存档原 ID 加入，并重置上一局的结束锁与菜单锁。
已占用端口但无法验证身份、旧版 mod 或进行中的对局会明确报错，不再拉起重复进程。
本次更新需要主机和猫娘都加载新 DLL；旧进程第一次升级仍需正常退出并重启游戏。
